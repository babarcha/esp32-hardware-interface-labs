# SPI Lab 03 — ESP32 SPI Master: Beginner Tutorial

## 1. Purpose and scope

This lab demonstrates the ESP32 SPI master driver through a reusable bus abstraction. It covers bus setup, logical device registration, synchronous write/read/full-duplex operations, argument validation, and resource cleanup. The current firmware has no external SPI peripheral connected; successful driver calls are **not** evidence of correct peripheral communication.

## 2. Learning objectives

After this lab, you should be able to explain the four common SPI signals, clock modes, full-duplex transfers, SPI bus/device handles, blocking transactions, transaction length units, and the distinction between driver-level execution and hardware-level verification.

## 3. SPI signals and wiring

| Signal | ESP32 GPIO | Function |
|---|---|---|
| MOSI | GPIO23 | Master-out, peripheral-in |
| MISO | GPIO19 | Master-in, peripheral-out |
| SCLK | GPIO18 | Clock generated by master |
| CS | GPIO5 | Active-low device selection |

A connected peripheral also needs a compatible power supply and shared ground. The lab uses `SPI3_HOST`. Multiple peripherals may share MOSI/MISO/SCLK, with separate CS lines.

## 4. SPI versus I²C

SPI is generally a clocked, full-duplex serial interface with a separate chip-select line. It does not use I²C-style bus addresses or ACK/NACK. An SPI device's register protocol and response timing are defined by its datasheet.

## 5. Clock modes

| Mode | CPOL | CPHA | Clock idle |
|---|---:|---:|---|
| 0 | 0 | 0 | Low |
| 1 | 0 | 1 | Low |
| 2 | 1 | 0 | High |
| 3 | 1 | 1 | High |

The example registers a Mode 0 device at 1 MHz. The peripheral datasheet must determine the correct mode and maximum clock frequency.

## 7. `main.c`: application flow

`app_main()` initializes the bus; registers a logical device with CS GPIO5, 1 MHz, Mode 0; prepares three transmit bytes `0x9A 0xBC 0xDE`; allocates a three-byte receive buffer; calls `spi_bus_transfer()`; prints transaction results; unregisters the device; and releases the bus.

This demonstrates the expected lifecycle, not a device-specific protocol. The printed RX bytes have no established meaning without a responding peripheral.

## 8. `spi_bus.h`: public contract

The header declares the bus lifecycle (`spi_bus_init`, `spi_bus_deinit`), device lifecycle (`spi_device_register`, `spi_device_unregister`), and transfer functions (`spi_bus_write`, `spi_bus_read`, `spi_bus_transfer`). Callers receive ESP-IDF `esp_err_t` status values. `spi_device_handle_t` represents a configured logical peripheral, not the physical SPI controller.

## 9. `spi_bus.c`: bus initialization

`spi_bus_init()` rejects duplicate initialization using the private `bus_initialized` flag. It configures MOSI, MISO, and SCLK pins; disables unused quad lines by setting them to `-1`; and invokes `spi_bus_initialize(SPI3_HOST, ..., SPI_DMA_CH_AUTO)`. The flag changes to true only on successful initialization.

## 10. Device registration

`spi_device_register()` checks that the bus is initialized, that the output pointer exists and does not already contain a handle, and that CS, frequency, and mode are within the wrapper's basic accepted range. It fills `spi_device_interface_config_t`, including `clock_speed_hz`, `mode`, `spics_io_num`, and `queue_size = 1`, then calls `spi_bus_add_device()`.

A successful registration configures the driver; it does not detect whether physical hardware is attached. Unlike I²C, SPI registration has no address-probe ACK.

## 11. Transaction representation

`spi_transaction_t` describes a single transfer. Its `length` field is measured in **bits**, not bytes. Thus `data_length * 8` converts a byte count into the bit count required by ESP-IDF. The implementation clears the transaction structure using `memset()` before filling the relevant fields.

## 12. Write-only operation

`spi_bus_write()` validates state, handle, pointer, and nonzero length. It sets `transaction.length` and `transaction.tx_buffer`, then calls blocking `spi_device_transmit()`. Data is shifted out on MOSI while SCLK runs.

## 13. Read-only operation

`spi_bus_read()` sets the receive buffer and requested bit length. The master must still generate SCLK to read from a peripheral. The actual bytes depend on the target device's protocol and what it drives onto MISO; a read operation does not automatically select a register.

## 14. Full-duplex operation

`spi_bus_transfer()` sets both `tx_buffer` and `rx_buffer` for the same clocked transaction. During each clock cycle, bits may be shifted out on MOSI and sampled on MISO. The example sends three bytes (24 bits). Without an external device, the RX buffer must not be treated as valid application data.

## 15. Synchronous versus queued operations

The wrapper uses `spi_device_transmit()`, a synchronous call that returns after the driver completes the transaction or reports an error. The device configuration includes `queue_size = 1`, but this example does not use asynchronous `spi_device_queue_trans()` or `spi_device_get_trans_result()`.

## 16. Error handling

The wrapper returns `ESP_ERR_INVALID_STATE` for operations that require an initialized bus and `ESP_ERR_INVALID_ARG` for null handles/buffers, zero-length transfers, or invalid registration parameters. Other error codes are propagated from ESP-IDF. The application checks each major call and prints `esp_err_to_name()` on failure.

## 17. Resource lifecycle

```text
spi_bus_init()
    -> spi_device_register()
    -> spi_bus_transfer()
    -> spi_device_unregister()
    -> spi_bus_deinit()
```

The device must be removed before the bus can be freed. The private initialization flag is cleared only when `spi_bus_free()` succeeds.

## 19. What has and has not been validated

The repository README reports that SPI initialization, device registration, transaction execution, device removal, and bus release have been exercised. There is currently no external SPI peripheral, so the exercise does not verify MOSI data reception, MISO response integrity, clock timing at the pins, or a real peripheral's protocol.

A completed build confirms compilation/linking. Flash/monitor logs confirm execution. A logic analyzer or real SPI peripheral is needed for stronger hardware-level validation.

## 20. Future MCP3008 integration

The MCP3008 ADC is a suitable future peripheral for SPI hardware validation. A follow-up lab should wire the ADC according to its datasheet, configure the supported clock and mode, send the appropriate command bytes, decode the ADC result, and compare measured voltages against known inputs. Do not infer MCP3008 readings from this generic three-byte demonstration.

## 21. Troubleshooting

- **Build command fails:** Check that the ESP-IDF terminal is activated and that the working directory contains this lab's `CMakeLists.txt`.
- **COM3 busy:** Close other serial monitors or applications using the port.
- **Initialization fails:** Check for another component claiming the same SPI host or GPIO resources.
- **Device registration fails:** Verify CS GPIO, clock speed, mode, and handle state.
- **Unexpected RX bytes:** Without a connected peripheral, this is expected and not a protocol result.
- **Bus deinit fails:** Remove registered devices before freeing the bus.

## 22. Design choices and tradeoffs

The wrapper isolates application code from ESP-IDF setup details, makes lifecycle checks explicit, and exposes a small reusable API. It deliberately uses blocking calls to keep the introductory lab understandable. Production systems may need transaction queuing, DMA-buffer constraints, bus sharing coordination, tighter timing requirements, and device-specific drivers.

## 23. Interview questions

**Why does SPI need chip select?** It identifies which peripheral participates in a transaction, since standard SPI has no I²C-style address field.

**Why is transaction length multiplied by eight?** ESP-IDF expresses SPI transaction lengths in bits; the wrapper API takes byte lengths.

**What is full duplex?** The master can shift data out and sample incoming data during the same clocked transfer.

**Does `ESP_OK` prove sensor communication?** No. It confirms the driver completed the requested operation, not that a sensor interpreted it or returned meaningful data.

**Why use separate bus and device handles?** The bus represents shared controller resources; each device handle stores peripheral-specific configuration such as chip select, clock, and mode.

## 24. Summary

This lab demonstrates a reusable ESP-IDF SPI master abstraction with explicit lifecycle management and synchronous transfers. The next stage is to validate real peripheral behavior, preferably with the MCP3008 and a logic analyzer, after documentation standardization across all four labs is complete.
